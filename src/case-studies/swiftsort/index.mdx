## Project landscape

<Prose>

SwiftSort sits in the **mid-mile** of the logistics value chain — the terminal (warehouse), where incoming goods are sorted and placed at delivery gates for last-mile drivers to pick up.

Every gate is assigned to a set of postal codes. Workers read the address label on each parcel, determine the correct gate, and stage it for the driver. That gate-lookup — label to destination — is the decision this project redesigned.

</Prose>

## The business goal

<Prose>

Drivers visited every customer stop daily — even for a single parcel. Too many stops, longer routes, underloaded trucks.

The business wanted to **accumulate goods by volume** and batch deliveries: instead of visiting stops A, B, C, D, E, F every day, a driver covers A, B one day, C, D the next, E, F the day after. Fewer stops, shorter routes, fuller trucks.

For this to work, workers needed to be **informed about drop-zone assignments frequently** — which gate to place each parcel at, updated as volume changes.

</Prose>

## The problem

<Prose>

Workers sorted entirely from memory. They read the address label, recalled which gate that postal code maps to, and decided the stacking order — all from experience. Gate assignments lived in their heads, not in any system.

That made the business goal impossible: you can't dynamically reassign gates when the worker's only reference is what they've memorized. And asking them to override that muscle memory with changing gate numbers was confusing — every update fought against years of internalized routing.

</Prose>

</Prose>

### The POC that proved the model

<Prose>

We built a proof of concept with minimal UX effort: **show the gate number on scan** so workers place goods where the system tells them, not where they remember.

The POC proved the business impact — fewer stops, shorter routes. And for UX, it doubled as preliminary usability testing: watching workers use it revealed the real interaction challenges — cognitive load, reach, and confirmation friction.

Gate assignment became **programmable**. Planners change routing based on volume; workers scan, see a gate, place it there. They don't need to know the strategy.

</Prose>

## How I approached it

<Prose>

I started on the terminal floor — shadowing operators across shifts, observing how goods got sorted and stacked, and interviewing terminal managers to surface workarounds no documentation captured.

The goal was not to invent a new workflow but to find the behavior that *already worked* and build the system around it.

</Prose>

## The moment that changed the design

<Prose>

During POC testing, operators struggled to reach the confirmation button on the mounted tablet — it was bolted in the only spot it fit, often out of arm's reach. The team's instinct: **make the button bigger, move the tablet.**

When I revisited the session recording, I noticed **every worker was already wearing a ProGlove scanner** — an input device they used constantly, without thinking. The tablet wasn't the problem; forcing a tap on an out-of-reach screen was.

I proposed a **static QR code** as the last card in the drop list. Scan it with the ProGlove, or tap it. Reach stops being a constraint.

</Prose>

## Working with engineering

<Prose>

Engineering initially proposed a **dynamic QR** — one generated per parcel. They flagged the complexity themselves: backend overhead, scalability risk, tight timeline.

We landed on **static QR** — simpler to build and better on the floor:

- **Reliable** — no backend to fail, works offline
- **Scalable** — same code works at every terminal
- **Zero-config** — operations place codes without IT

</Prose>

## A second win, surfaced by the business

<Prose>

A discovery session with ops leads revealed that drivers with **several items for the same destination** had to scan and drop each one separately — repetitive and slow at volume.

In a brainstorm with the tech lead and PO, we shaped the solution: **group everything bound for one destination and drop it in a single scan.**

</Prose>

## How the work got made

<Prose>

**Figma Make** generated LIFO card layout variants — I tested each against one question: readable at arm's length, in motion, with gloves? **MS Copilot** clustered field notes into themes (that is how the priority insight surfaced). **Banani** structured the stacking flow before I committed it to high-fidelity in Figma.

~30% faster early exploration — but every shipped decision was validated on-site.

</Prose>

## What we shipped knowingly incomplete

<Prose>

One known gap: **drop-off location editing and parcel grouping don't behave as cleanly as designed.** We shipped deliberately — the data behavior at production volume was unpredictable from a design tool, so we instrumented the release to learn from real usage rather than model assumptions.

</Prose>

## The takeaway

<Prose>

SwiftSort was not a UI redesign — it was a redesign of **decision architecture**. Sorting shifted from memory-dependent to system-guided, from tenure-correlated to scalable from day one. The highest-impact move: removing cognitive constraints by building on motor patterns workers already had.

</Prose>
